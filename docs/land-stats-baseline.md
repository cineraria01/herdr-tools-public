# 착지 기준선 — 병합기 도입 전 고정 숫자 (2026-11-20)

**병합기 도입 전**의 착지를 잰 고정값이다. 다시 계산하지 않는다. 다른 대책은 이미 일부 들어와 있던 때다 — rerere는 11/16부터 쓰였고, 문서 조각은 11/19에 처음 착지했고, 검증 시간 표본은 11/20까지다. 그래서 이 표는 **병합기 효과**의 비교 기준이고, rerere·문서 조각·겹침 경고 같은 개별 대책의 효과에는 적용 시점으로 나눈 자료를 따로 써야 한다.

대책 뒤 숫자는 병합기 자기 일지에서 잰다(병합기가 켜지면 착지는 한 기계·한 프로세스만 하므로 일지 하나로 된다 — 아래 「비교할 때」).

**정의가 다르다**: 아래는 옛 착지 로그의 파일 이름·수정 시각·`▸` 줄과 레인 보고(`events.tsv`)를 긁어 낸 값이다. 병합기 일지로 잰 같은 이름의 지표와 그대로 빼서 효과로 읽지 말고, 차이의 방향과 크기를 본다.

## 비교할 때

- 병합기·트레인 확대 기준(아스트라 결정 검토): 비슷한 착지 각 100건에서 **완료 → 착지 상위 10% 20% 단축, 착지 건당 무거운 재검증 50% 감소, 폐기분을 포함한 총 검증 시간 증가 없음**. 「재검증 50%」는 전후 모두 **같은 원인(base 이동·묶음 쪼갬 등)으로 무거운 검증을 다시 돈 실제 횟수**를 같은 분모(착지 건수)로 세서 판정한다 — 위 71회(차례 양보 결정)를 그 분자로 쓰지 않는다.
- 대책 뒤 숫자는 병합기 일지에서 잰다(병합기 2판 몫): 제출 → 착지 p50·p90, 묶음 크기, 착지 건당 검증 횟수·시간(폐기분 포함, 원인별), 돌려보낸 수(까닭별).
- **착지 1건** = 기본 브랜치 ref를 `from != to`로 한 번 옮긴 것. 도착 SHA(40자)와 그 이동에 든 제출 수(묶음 크기)를 따로 적는다 — 한 번의 이동에 커밋이 여럿 들어가도 착지는 1건이다.
- **완료 → 착지**: hc-lane `events.tsv`의 「완료」 줄을 **작업 ID로** 잇는다 — 직전 착지 뒤의 그 작업 첫 「완료」부터. 선행 조건: `events.tsv`에 작업 ID 칸이 생긴 뒤의 기록만 잇고, 작업 ID 없는 표본은 수를 따로 적는다. 위 72분·268분은 보고 줄끼리 이은 값이라 같은 정의가 아니다.
- 대응 관계: 「완료 보고 → 착지 보고」 ↔ 일지의 완료 → 착지, 「멈춤: rebase 충돌 · 문서 번호 겹침 · 검증 실패」 ↔ 일지의 돌려보낸 까닭.
