# hc-lane 이어 띄우기 (--revive)

```sh
hc-lane --revive [--on <기계>] --brief <지시문> --name <레인> --repo <저장소> [-- <실행 명령…>]
```

- 쓰는 때(2026-11-28 ht-lane-revive): 워커 기계 전원이 끊겨 레인 터미널(에이전트 세션)만 죽고, 작업 트리·가지·커밋 안 된 변경·대화 기록·레인 임대는 디스크와 원격에 남았을 때.
- 방식은 업계의 「같은 이름·같은 디스크로 다시 붙이기」다: 일(작업 트리·가지·임대)과 실행(터미널)을 나눠, 죽은 실행만 새로 띄워 같은 작업 폴더에 붙인다.
- 인자는 보통 띄우기와 같고(`--on`·`--branch`·`--start-wait`·`--dry-run`·`--direct`·`-- <실행 명령>`), `--brief`가 꼭 있어야 한다.
  `--read`·`--resume`·`--carry`와는 함께 쓰지 않는다(인자 오류 종료 1).
- 대기열(`hc-fill revive`, [이어 띄우기](../hc-fill/revive.md))은 run 지시문을 스스로 두고(절은 `--print-steps --revive`로 받는다) `--brief` 대신 `--continue-from <그 사본 경로>`를 준다 — 대화는 첫 사용자 글이 그 경로로 시작하는 세션을 고른다(대기열 레인의 첫 지시 「<runs/<레인>-run.md> 지시문을 읽고 진행하라. …」). `--continue-from`은 `--brief` 없이 `--revive`와만(아니면 인자 오류 종료 1).

## 띄우기 전에 보는 것 (아무것도 쓰기 전에)

- 작업 트리(`<저장소>.wt/<브랜치>`)가 있고 그 폴더가 git 작업 트리의 맨 위이고 그 가지가 레인 가지여야 한다 — 아니면 입력 거절 종료 11.
  진행 중인 rebase(HEAD가 떨어짐 — git이 그 가지를 어느 작업 트리에도 걸지 않는다)는 rebase의 `head-name`으로 가지를 읽는다.
- 그 작업 트리(아래)를 지금 폴더로 쓰는 살아 있는 터미널이 있으면 `hc-lane: 이미 돎 — …`과 종료 10, `hc ls`를 못 읽거나 대상 기계 연결을 모르면 종료 1.
  판정은 `hc-lane gc`·`clean`과 같은 함수다(이 기계는 디스크로 같은 폴더인지까지 — 다른 철자 cwd도 쓰는 중, 띄운 뒤 cd로 들어온 터미널도, Windows 꼴 cwd는 다른 폴더).
- 레인 임대는 새로 잡지 않는다: 지금 값(`hc-lane lease show`)의 주인(제목 `hc-lane lease <레인> <기계> <UTC>`)이 같은 레인·같은 기계(`--on`이면 그 기계 이름, 아니면 `hostname -s`)일 때만 그 값을 `HC_LANE_LEASE`로 이어 쓴다.
  주인이 다르면 「이미 돎」 종료 10, 조회 실패는 종료 1.
  `--revive`의 10은 「살아 있는 실행이 있다」는 결정적 실패를 `hc-fill revive`가 「이미 돎」으로 따로 받게 남긴 것이다(대기열 바퀴는 `--revive`를 쓰지 않는다 — 실패 종류 표 [hc-lane 띄우기](launch.md)).
  임대가 없으면 종료 11 — 착지·clean으로 끝났거나 손으로 놓은 레인이라 이어 띄우지 않는다(다시 일하려면 보통 띄우기).
  원격 없는 저장소는 보통 띄우기처럼 임대 없이 띄운다.

## 띄우기

- 작업 트리 만들기·설정 훅(`.claude/herdr-setup.sh`)·실어 온 자료 풀기·임대 잡기를 건너뛴다.
  작업 트리의 파일에 손대지 않는다(reset·stash·checkout·clean 없음).
  `hc run`이 거절하거나 실패해도 보통 띄우기의 되돌리기(고유 커밋이 없으면 작업 트리 지움)를 하지 않고 `작업 트리 … 는 그대로 둠(--revive)`.
- 터미널 이름·라벨(`hc-lane=1`·`herdr.space`)·레인 환경(주인 지휘·우선 등)·지시문 사본 자리·시작 확인·레인 기록은 보통 띄우기와 같다(대기열이 그 터미널을 평소처럼 읽는다).
- 지시문 사본은 원래 지시문 + 착지·정리 절차 + **「재시동 뒤 이어 가기」 절**이다: ① `git status`와 진행 중인 rebase·merge를 먼저 본다 ② 반쯤 쓴 파일을 확인한다(되돌리거나 stash하지 않는다) ③ 마지막 보고(`hc-lane events --lane <레인>`)가 「완료」이고 그 sha가 HEAD와 같으면 같은 줄(`hc-lane report 완료 HEAD …`)을 이 실행으로 한 번 더 부르고 판정을 기다린다(대기열 감사는 실행마다 열려 앞 실행의 판정은 새 실행에 오지 않는다 — ht-revive-cmd) — 아니면 이어서 일한다.
- 대화 기록: 대상 기계에서 그 작업 트리의 Claude 대화 기록(`${CLAUDE_CONFIG_DIR:-~/.claude}/projects/<폴더 이름>/*.jsonl`, 폴더 이름은 작업 트리 실제 경로(`pwd -P`)의 영숫자 밖 글자마다 `-`)을 새것부터 보고, 첫 사용자 줄의 글이 이 레인 지시문 사본 경로로 시작하는 첫 세션을 골라 레인 환경에 `HC_LANE_CONTINUE=--resume=<세션 id>`(한 낱말 — zsh는 따옴표 없는 변수를 낱말로 나누지 않아 `--resume <id>` 두 낱말은 한 인자로 넘어가 claude가 「unknown option」으로 뜨지 못한다, 감사 atp68z5 중간 1)를 넣는다.
  같은 폴더에는 같은 기계에서 그 작업 트리를 cwd로 뜬 자동 감사(`--read`) 대화도 있어, 「가장 새 대화」(`--continue`)를 잇지 않고 레인 자신의 대화를 고른다(감사 atp67l6 중간 1 — 레인이 판정을 기다리는 동안 꺼지면 가장 새 대화는 감사 쪽이다).
  실행 명령 틀이 CLI 인자 자리에 `$HC_LANE_CONTINUE`(따옴표 없이 — 없으면 사라진다, sh·zsh 같음)를 두면 이어 가고, 고를 세션이 없거나 틀에 그 자리가 없으면 같은 지시문으로 새로 시작한다.
  예: `zsh -c 'exec claude $HC_LANE_CONTINUE --model … "$1"' _ {task}`.
  확인이 실패하면 띄우지 않는다(종료 1). 아주 긴 경로(Claude가 이름을 잘라 해시를 붙이는 약 200자 넘음)는 찾지 못해 새로 시작한다.
- 쌓아 띄운 레인(`HC_LANE_STACK`)도 선행 제출을 다시 확인하지 않는다(작업 트리가 이미 있어 시작점을 쓰지 않는다). 그 환경은 레인 환경에 그대로 넘긴다.

## 실측 (2026-11-28, 설계가 확인 못 한 셋)

- `claude --continue`는 작업 폴더별 대화를 고르고, 앞 프로세스가 끝난 뒤에도 잇는다: 폴더 A에서 짧은 세션을 끝낸 뒤 A의 `--continue`는 앞 대화를 기억했고, 기록 없는 폴더 B의 `--continue`는 몰랐다.
  `--continue`는 앞 대화를 복사한 새 세션 파일을, `--resume <id>`는 같은 파일에 덧붙인다 — 둘 다 첫 사용자 글은 그대로라 이어 간 뒤에도 레인 세션으로 골라진다(`--resume <id>`도 끝난 세션을 기억했다).
  zsh 틀 `env HC_LANE_CONTINUE=--resume=<id> zsh -c '… claude $HC_LANE_CONTINUE -p …'`(계정 풀 감싸개를 거쳐)도 끝난 세션을 기억했다.
- 닫힌 터미널의 `hc get <옛 주소>`는 종료 0에 `state` `finished`·`reason` `killed`이고 `cwd`가 그대로 남는다. `hc ls`(`--all` 없이)에는 빠진다 — 그래서 쓰는 터미널 판정은 `hc ls`로 한다.
- 손으로 `hc run`해 띄운 터미널의 라벨에는 `hc-lane=1`이 없다(그 기계의 `where`만). `hc get`에는 환경 칸이 없고, 레인은 `env HC_LANE_LEASE=…`가 `argv`에 보인다.
