# hc-fill: 먼저 띄움

- **먼저 띄움**(2026-11-18 — 큰 일을 계약 → 바탕 → 영역으로 쪼개면 대기열 거의 모두가 한두 선행에 묶여, 자리가 30분 넘게 비어도 띄울 것이 없었다): 띄울 수 있는 것을 다 띄우고도 자리가 남으면, 선행이 「아직」인 대기 레인(판정 못 함 — fetch 실패 등 — 은 빼고, `add --no-early` 줄도 빼고)을 같은 차례(우선순위·넣은 차례)로 띄운다.
  선행 가운데 대기열에 아직 안 뜬(`wait`) 레인이 있는 줄은 빼서 그 선행이 자리를 먼저 잡게 한다(그 선행이 이번 바퀴에 떴으면 — 먼저 띄움 포함 — 후보. 대기열 밖 선행은 그대로) — 뒤 레인이 자리를 다 먹으면 선행이 못 떠 기한까지 교착했다(감사 [중간] 1).
  run 지시문 끝에 「먼저 띄움」 절이 붙는다: ① 지금은 준비만(지시문·계약 읽기, 자기 몫 파일의 실패 시험·골든 고정, 선행이 고칠 파일은 아직 안 고침) ② `until git fetch -q origin && <선행마다 따로 한 줄: 커밋 제목 머리 판정 또는 대기열 선행이면 착지 표식(`git ls-remote` + `git merge-base --is-ancestor`) — 위 선행 판정과 같은 규칙> do … sleep 180; done`으로 기다림(배경 실행 금지 — `&`·nohup도 도구의 run_in_background도, 명령 시간 한도는 도구 최대로, 기한은 띄운 시각 + 설정 `early_wait`시간(기본 5)의 고정 시각 — 넘은 뒤 `hc-lane early-wait`가 선행이 살아 진행 중이라고 하면 계속 기다리고(아래 「선행 사슬」), 아니면 「선행 대기 초과」를 `hc-lane report 막힘`하고 멈춤) ③ 선행이 들어가면 `git rebase origin/<기본>` 뒤 본 작업. 대기열 14번째 칸이 `early`가 되고 `ls`에 「먼저 띄움(선행 …)」 — 떠 있는 동안은 local 저장소의 지금 있는 `origin/<기본>`으로(ls는 fetch하지 않는다 — 참조가 낡으면 다음 run의 fetch까지 늦게 보인다) 선행마다 판정해 「먼저 띄움(선행 들어감 — 본 작업)」·「먼저 띄움(선행 기다림 b · 들어감 a)」, 판정 못 하면(저장소 줄 없음·참조 없음) 띄울 때 그대로, 끝난 레인도 그대로(2026-11-19 — 띄울 때 적힌 비고만 보고 본 작업 중·착지한 레인을 「선행을 기다림」으로 두 번 틀리게 보고했다).
  살아 있는 먼저 띄움 레인 수의 상한은 설정 `early`(키 혼자·빼면 남은 자리 전부, `0`이면 끔).
  같은 선행에 묶인 레인끼리도 함께 띄운다 — 파일 겹침은 아래 「겹침」(설정 `overlap`)이 본다(`block`이면 다른 쓰기 소유 레인과 예약이 겹치는 줄은 먼저 띄우지 않는다 — 자기 선행 사슬의 예약은 세지 않고 착지 뒤 rebase, 2026-11-24 early-own-chain).
  선행의 산출물 없이는 준비조차 못 하는 레인은 `add --no-early`로 넣는다.
  기한을 넘겨 「선행 대기 초과」로 멈춘 먼저 띄움 레인은 대기열 줄이 떠 있음(`up`)으로 남아 선행이 들어가도 다시 뜨지 않는다 — 지휘가 `hc-fill rm <레인>` 뒤 다시 넣는다(보통 레인의 막힘과 같은 규칙).
