# hc-fill: 반송 다시 띄우기

2026-11-26 ht-bounce-relaunch — 병합기가 검증 실패로 반송한 제출의 레인은 이미 끝나 있었고, 대기열 줄은 「감사 통과 — 대기열이 제출함」으로 남아 지휘가 `-r2` 레인을 손으로 넣어 커밋을 cherry-pick했다.

- 자동 다시 맞춤(`reland.go`, 도움말 `hc-fill help run`)과 같은 바퀴(`reland`)·장부(`reland.tsv`)·횟수(`reland_max`)·원래 레인에 보냄(`reland_wait`)을 쓴다.
- rebase 충돌(「착지 실패(종료 3, 충돌 …)」)은 지금처럼 `<레인>-reland` 줄이다.
  - 지휘가 `hc-fill rm`으로 뺀 레인(대기열에 그 줄이 없고 일지에 rm 기록)은 넣지 않고 `반송 다시 띄움 안 함 <레인>: 대기열에서 지워진 레인(…)` 한 줄, 장부 `줄 없음`(2026-11-28 — 11-27 rm 직후의 반송이 `-reland`로 닫은 레인을 되살렸다). 넣기 직전 대기열 잠금 안에서 한 번 더 본다(rm은 줄 빼기와 일지를 같은 잠금 안에서 한다). 일지를 못 읽으면 다음 바퀴에.
  - 대기열 밖에서 띄운 레인(줄도 rm 기록도 없음)은 지금처럼 넣는다. `-reland`를 넣은 뒤 원래 줄을 빼면 넣은 줄은 그대로다(넣음 알림을 받은 지휘가 그 줄도 뺀다).
- 그 밖의 반송(「병합기: 착지 실패(종료 …」 + `refs/merge-failed/<n> 로 옮김`)은 그 레인의 대기열 줄을 다시 띄운다.
- 지휘가 거둔 제출(이 기계의 「지휘가 거둠: <까닭> — 원본 …」 막힘 사건, [거두기](withdraw.md))도 같은 길이다 — 절에는 병합기 로그 대신 그 까닭.
- 다시 띄우지 않는 때(장부 결과 칸):
  - `줄 없음` — 대기열에 그 레인 줄이 없다(지휘가 `rm`).
  - `줄 바뀜` — 줄이 떠 있지 않다(지휘가 바꿈).
  - `이미 main` — 반송 커밋이 모두 기본 가지에 있다(`git cherry` — 다른 이름으로 cherry-pick해 들어간 것도, 못 보면 다음 바퀴에).
  - `상한` — 같은 레인이 `reland_max`번 넘게 다시 맞춤·다시 띄움을 받아 주인 지휘에 막힘으로 넘긴다.
  - `넘김` — 원래 레인에 보냈는데 `reland_wait`분 안에 다시 안 냈고 그 레인이 아직 살아 있어(같은 이름·작업 트리가 겹친다) 주인 지휘에 막힘으로 넘긴다.
- 다시 띄움: 절 파일 `bounce/<레인>.md`를 먼저 쓰고, 줄을 같은 줄 ID로 `wait`·14칸 `bounced`(감사 칸 그대로)로 돌린 뒤, 장부 `다시 띄움`·주인 지휘에 중간 한 줄.
- `hc-fill status`·`ls`는 그 줄을 「반송됨 — 다시 띄움 대기」로 보인다.
- 다음 띄우기는 같은 이름의 옛 실행 터미널을 채택하지 않는다 — 제출하고 끝내 쉬면 닫고(주차의 `parkClose`와 같은 길, 마지막 보고 「제출」), 아니면 「같은 이름 반송된 옛 실행 터미널 살아 있음」으로 기다린다(hc-lane이 같은 이름을 거절한다).
- 다음 띄우기는 run 지시문 끝에 반송 절을 붙이고(절 파일을 못 읽으면 띄우지 않는다), 띄운 뒤 14칸을 `-`로 지운다.
- 반송 절의 순서: `git fetch origin refs/merge-failed/<n>` 뒤 `git reset --keep FETCH_HEAD` → `git rebase origin/main` → 실패 줄의 원인만 고쳐 커밋(레인 탓이 아니면 막힘) → 감사·착지 절차대로 다시 제출.
- 반송 절에는 병합기 로그의 「실패 줄」 묶음(없으면 끝 20줄)과 지휘 메모(`hc-fill note`가 레인 기계에 남긴 `coord-notes.md`, 레인이 끝난 뒤 남긴 것도)를 싣는다.
- 반송 커밋에서 시작하는 길은 `hc-lane --resume`(주차 가지 전용 — 반송된 제출 가지는 거절) 대신 절의 fetch·`reset --keep`이다(다시 맞춤 지시문과 같은 길).
