# hc-sweep: 정말 쉬는가 (상태는 쉼인데 안에서 일이 도는 터미널)

- 일(2026-11-28): hc 상태 done이 33분 그대로인 Claude 레인 터미널을 R2가 닫아, 그 안에서 1시간 50분째 조용히(출력 0바이트) 돌던 배경 셸 셋이 죽었다(그 출력 파일 끝이 닫힌 그 초에 `[killed]`).
  - 처음에는 제보 문구(「배경 하위 에이전트를 기다리던 중」)로 하위 에이전트 셋이 죽은 것으로 보고 하위 에이전트 기록만 봤다(첫 고침). 세션 기록으로 다시 보니 그 셋을 띄운 하위 에이전트는 이미 끝나 있었다(meta `finished`·끝 줄 end_turn) — 죽은 것은 **끝난 하위 에이전트가 run_in_background로 남긴 배경 셸**이고, 하위 에이전트 기록만으로는 못 본다(ht-sweep-busy-tasks).
  - 화면 무늬(`busyRe` — 화면 끝 6줄의 `· N shell`)도 못 봤다: 배경 에이전트가 있으면 Claude가 모드 줄 아래에 에이전트 목록(`◯ <종류>  waiting on 1 shell · …`, `↓ 1 more`)을 그려, 목록이 다섯 줄을 넘으면 모드 줄이 끝 6줄 밖으로 밀리고 목록 줄은 `·` 없이 `on 1 shell`이라 무늬에 안 걸린다(하위 에이전트 여섯으로 재현). 그래서 화면이 아니라 파일로 본다.
- 뿌리: hc 상태(코어가 화면으로 읽는 에이전트 상태)의 done·idle은 「주 대화의 턴이 끝났다」일 뿐 「안에서 도는 일이 없다」가 아니고, 코어의 판정은 이 저장소 밖이라 닫는 쪽이 스스로 확인한다.
- 실측(Claude Code 2.1.332, 배경 하위 에이전트가 python sleep을 도는 동안 20초 간격):
  - 코어 상태는 판에 따라 done(지휘 기계 사고)이거나 working·turn 0(hc 0.1.22 워커)이었다 — 믿을 수 없다.
  - 세션 파일(`~/.claude/sessions/<pid>.json`)의 status는 주 턴이 끝나면 idle이었다(하위 에이전트가 도는데도).
  - 자식 프로세스는 하위 에이전트가 Bash를 쓰는 동안만 생기고(zsh·python), 도구 사이에는 MCP·caffeinate뿐이라 늘 있는 것과 가르기 어렵다.
  - 화면 끝 줄은 쉬는 세션에서도 계정 사용량 표가 저절로 바뀐다(23% → 24%) — 화면 변화는 신호가 못 된다.
  - 대화 기록: 하위 에이전트는 `~/.claude/projects/<폴더 이름>/<세션 id>/subagents/agent-<id>.jsonl`·`.meta.json`에 쌓이고, 도는 동안 meta에 `finished` 칸이 없다가 끝나면 `"finished":true`가 된다. 도구 한 번(45초)이 도는 동안은 jsonl이 바뀌지 않는다.
- 고른 신호(공용 꾸러미 `internal/rest` `Of` — 좋음(쉼)·활동·모름, hc-sweep은 `cmd/hc-sweep/rest.go` `quiet`로 부른다):
  - 그 터미널 pid와 자손에서 처음 찾은 세션 파일의 `sessionId`로 그 세션의 기록만 본다(같은 폴더를 함께 쓰는 남의 세션은 치지 않는다). 폴더 이름은 셈하지 않고 `projects/*/<세션 id>`를 찾는다(Claude 판마다 이름 꼴이 달라도 같다).
  - 활동: 기록(meta·jsonl)이 `sweep_r3` 안에 바뀐 하위 에이전트에 끝난 증거가 없다(meta 꼴·종류와 상관없이 — 증거가 없으면 닫지 않는 쪽. r3 넘게 조용하면 죽은 것으로 보고 치지 않는다).
  - 끝난 증거(`agentEnded`)는 그 하위 에이전트 자기 기록 둘뿐이다(하나라도): ① meta `"finished":true`(끝까지 간 배경 에이전트) ② 자기 기록 끝 64KB의 마지막 대화 줄(type user·assistant)이 assistant `"stop_reason":"end_turn"`(그 뒤 훅 결과 줄은 건너뜀 — 도구를 쓰는 중이면 assistant tool_use나 user tool_result). 둘 다 없고 r3 안에 바뀌었으면 활동이다.
  - ②는 「팀원」 때문이다: Agent 도구에 `name`을 준 배경 하위 에이전트는 meta에 `"taskKind":"in_process_teammate","teamName":"session-…"`가 붙고 `finished` 칸이 아예 없으며, 일을 마치고 쉬면 자기 기록 끝이 end_turn이다(감사 atp6tdq M1 — 이 기계 팀원 기록 332개 모두).
  - 주 기록의 끝남 알림(`<task-id><에이전트 id></task-id>`)은 증거로 쓰지 않는다(지휘 결정 2026-11-28, 감사 atp6urq M1): 멈춘 것 3개(기록 644개 가운데)를 위해 넣었다가, 다시 불린 에이전트 69건을 앞 알림 때문에 「끝남」으로 읽었다. 잘못 닫으면 일을 잃고 잘못 남기면 늦게 닫힐 뿐이다(r3 상한).
  - 다시 불린 하위 에이전트(SendMessage)는 활동으로 읽힌다: 다시 부르면 meta의 `finished`가 지워지고 도는 동안 끝 줄이 tool_use다.
  - 활동(배경 작업): 그 세션의 배경 작업 출력 파일 가운데 끝 표시가 없고 `sweep_r3` 안에 생기거나 바뀌었고 **살아 있는 프로세스가 그 파일을 쥔** 것이 있다(`bgTasks` — `배경 작업 N개 도는 중`, 하위 에이전트와 함께면 ` · `로 한 줄).
    - 자리: `<뿌리>/claude-<uid>/<폴더 이름>/<세션 id>/tasks/<작업 id>.output`. 뿌리는 Claude 자신의 규칙대로 `$CLAUDE_CODE_TMPDIR` 또는 `/tmp`(맥은 `/private/tmp`)다 — 레인의 작업별 TMPDIR은 따르지 않는다. 리눅스도 같은 코드다(Claude 2.1.332 바이너리 `Dp()`).
    - 폴더 이름은 셈하지 않고 `*/<세션 id>/tasks`를 찾는다. 하위 에이전트가 띄운 셸도 주 세션 폴더에 든다.
    - 세는 것: 일반 파일 `*.output` — run_in_background 셸, Monitor, 시간을 넘겨 배경으로 넘어간 전경 명령이 모두 같은 꼴이다. 링크(`a….output` → 하위 에이전트 기록)는 안 센다(하위 에이전트는 위 규칙). 끝난 전경 명령의 파일은 Claude가 지운다.
    - 끝 표시: 파일 끝이 `\n[exited with code N]\n`(끝남, N이 `unknown`일 수도) 또는 `\n[killed]\n`(TaskStop·터미널 닫힘)으로 끝난다(끝 64바이트만 읽는다 — 출력 가운데의 같은 글은 끝이 아님). 모르는 끝 글(다른 Claude 판)은 도는 중으로 읽는다(닫지 않는 쪽, r3까지).

      - 실측: 도는 배경 셸·도는 전경 명령의 파일은 그 셸과 자식이 쥔다(파일마다 프로세스 2 — 크기 0·수정 시각이 오래돼도). Monitor는 이 폴더에 파일을 만들지 않는다.

      - 안 쥔 미완도 수정 시각은 지금처럼 마지막 활동에 든다(쉰 시간은 그때부터).
      - 막 생긴 파일(프로세스가 열기 전 찰나)은 따로 두지 않았다: 실측에서 띄운 직후 이미 쥐어 있었고 그 틈은 밀리초다. 그 틈에 걸려도 그 파일의 수정 시각이 마지막 활동이라 hc-sweep의 닫기(`settle`)는 쉰 시간을 지금부터 다시 센다.

- 기록: 쉼 판정으로 남긴 터미널은 실제 쓸기에서 `남김: <주소> <이름> — 안에서 일이 도는 중(<신호>)` 또는 `— 쉼 모름(<까닭>)` 한 줄을 찍고 `~/.claude-tasks/closed.log`에 「남김(안에서 일이 도는 중)」·「남김(쉼 모름)」을 적는다 — 같은 주소·이름·세션·종류는 한 번만(바퀴마다 되풀이하지 않음).
- `--dry-run`은 판정과 까닭만 찍고 closed.log에 쓰지 않는다.
- 닫지 않은 터미널의 작업 임시 폴더는 그대로다(작업 임시 지우기는 닫힘을 따른다 — [작업별 임시 폴더](job-tmp.md)).

- 같은 함수를 hc-fill 표시(「작업 중(done)」·놀고 있음)가 나중에 쓸 수 있게 `rest.Of(t, now, r3, ps, held)`는 hc get 답 하나와 ps·열린 경로 읽기만 받는다.

## 한 문: 닫거나 손을 뗀 것으로 치는 길 모두 (ht-rest-one-gate, 2026-11-28)

- 일: hc-sweep을 두 번 고친 뒤에도 같은 믿음(「hc 상태 done·idle = 끝났다」)으로 터미널을 닫거나 레인이 손을 뗀 것으로 치는 곳이 여섯 더 있었다(아래 표). 곳마다 검사를 복사하지 않고 판정을 공용 꾸러미 `internal/rest` 한 곳으로 옮겨 모두가 그것을 거친다(단일 관문 + 모르면 하지 않음).
- 이 실측은 판 하나(위)의 것이다 — 세션의 판 묶음이 실물 점검을 통과하지 않았으면 이 판정은 모름이다(판이 바뀌면 같은 대조를 진짜 세션에 다시 돌린다, [상대 판 확인](upstream.md)).
- 판정은 그 터미널이 있는 기계에서만 된다(그 기계의 `~/.claude`·임시 뿌리). 그래서 다른 도구·다른 기계는 **묻는다**: `hc-sweep --rest <주소>`(읽기만, 쓸기 잠금과 따로)가 이 기계 터미널 하나의 판정을 한 줄로 찍는다 — `REST<탭>quiet|busy|unknown<탭><세션 id|-><탭><까닭|-><탭>end`(종료 0, `hc get` 실패도 모름 줄). r3은 그 기계의 `sweep_r3`.
  - 부르는 쪽은 `rest.Ask`: 주소에 다른 기계 접두(`기계/tN`)가 있으면 `hc exec --on <기계> --timeout 60 -- hc-sweep --rest tN`, 없거나 이 기계면 바로 `hc-sweep --rest tN`(hc-job-server는 `HC_JOB_HC` 곁의 hc-sweep — launchd PATH에 기대지 않는다).
  - 마지막 REST 줄 하나만 읽는다(경고 줄이 섞여도 된다). 종료 ≠ 0(옛 판 hc-sweep은 `--rest`를 몰라 종료 2·연결 안 됨·시간 넘김)·줄 없음·칸 수가 다름·끝 칸 `end` 없음(잘림)·모르는 상태는 모두 **모름**이다 — 배포 사이(지휘 기계가 먼저 새 판, 워커가 몇 분 뒤) 옛 판 워커는 늘 모름으로 읽혀 기다렸다가, 새 판이 되면 다음 바퀴에 그대로 닫힌다.
  - 묻기는 닫거나 제출하려는 그 터미널 하나에만, 앞의 싼 검사(이름·실행·상태·마지막 보고)를 다 지난 뒤에만 한다 — 바퀴마다 다 묻지 않는다.
- 조치별 규칙:

  | 자리 | 조치 | 활동 | 모름 | 모름의 상한 |
  |---|---|---|---|---|
  | hc-sweep `settle` | R1·R2·R3 닫기 | 안 닫음 | R3만 닫음 | `sweep_r3`(지금 그대로) |
  | hc-fill `endClose`(주차·반송 닫기) | 레인 터미널 닫기 | 안 닫음, 「… 남김: 안에서 일이 도는 중(…)」, 다음 바퀴 | 안 닫음, 다음 바퀴 | 그 기계의 hc-sweep이 나중에 닫는다 |
  | hc-fill `aCloseTerm`(감사 터미널, 수거 뒤·판정 넘긴 뒤) | 감사 터미널 닫기 | 안 닫음, 「감사 터미널 남김 …」 | 같음 | 지금 상한 그대로: `audit_close`바퀴 · 수거 뒤 「정리 필요」 한 번 |
  | hc-lane clean `auditCloseBusy` | 끝난 감사 터미널 닫기 | 안 닫음, 「끝난 감사 터미널 <주소> 남김 — …」, termGate가 지금처럼 멈춤 | 같음 | 지금처럼 clean 멈춤 → hc-fill 바퀴·hc-sweep |
  | hc-fill `oaFinish`·`oaClose`(운영 에이전트) | 턴 끝남으로 치기 · 닫기 | 끝으로 안 침 · 안 닫고 다음 띄우기 직전에 다시 | 같음 | `ops_agent_timeout`(시간 넘김이면 끝 — 그래도 닫기는 쉼일 때만) |
  | hc-job-server `step` | 멈춘 루프 끄고 다시 띄움 | 안 끔(까닭은 바뀔 때만 한 줄) | `HC_JOB_STALE`의 네 배(기본 6시간 — hc-sweep R3 기본과 같다) 넘게 그대로일 때만 끔 | 그 네 배 |
  | hc-fill `aAutoSubmit` | 대기열이 레인 대신 제출 | 안 제출, 판정은 턴 중일 때처럼 전달(깨우기 간격 그대로 — 레인이 스스로 받는다), 글 끝에 「대기열이 대신 제출하지 않았다: 레인 터미널 안에서 일이 도는 중(…)」 | 같음(까닭 「쉼 모름(…)」) | 깨우기(지금 흐름) |

  - 쉼이면 모두 지금 동작 그대로다. 활동이 r3 넘게 그대로면 판정이 쉼으로 바꾼다(끝없이 남지 않는다).
  - 자동 제출만 활동을 모름과 같게 친다(2026-11-28 ht-autosubmit-busy-wake — 감사를 통과한 done 레인에 잊힌 기다림 셸 넷이 돌아 「제출 미룸」만 18바퀴, 지휘가 손으로 깨웠다): 닫기와 달리 전달은 레인에서 아무것도 거두지 않고, 배경 작업이 아직 필요한지는 그 레인만 안다. 전달 뒤 쉼이 되면 레인이 아직 받지 않았을 때만 대기열이 제출한다(수거 표시는 먼저 만든 쪽만 이긴다).
  - `hc-sweep --rest`에 다른 기계 주소(`기계/tN`)를 주면 이 기계 자료로 판정하지 않고 모름(「다른 기계 주소 — …」)이다 — 사람이 손으로 물을 때는 그 기계에서 `hc exec --on <기계> -- hc-sweep --rest <tN>`.
  - hc-job-server는 묻기 자식의 PATH 앞에 `HC_JOB_HC` 폴더를 둔다 — `--rest`가 안에서 `hc`를 PATH 이름으로 부르는데 launchd PATH에는 `~/.local/bin`이 없을 수 있다(감사 atp7a3w M1, 없으면 늘 「hc get 실패」 모름이라 멈춘 루프가 6시간 뒤에야 꺼졌다).
- 문을 건너뛰지 못하게: `internal/rest` `TestEveryKillGoesThroughGate`가 저장소 모든 도구(`cmd/*/*.go`)에서 `hc kill`과 대기열 제출(`asubRun`)이 같은 함수 안에서 `rest.Ask` 뒤에만 있는지 본다. 판정 없이 닫아도 되는 것은 그 시험의 목록뿐이다(까닭 한 줄씩): hc-sweep `closeTerm`(settle이 낸 쉼만 받음 — `TestEveryCloseGoesThroughSettle`), hc-fill `reviveShellClose`(재시동 뒤 셸만 남은 빈 셸), 병합기 `termKill`(추측 검증 일꾼 터미널 — 에이전트 아님).
